## Как устроено

```
микрофон → Vosk / sherpa-onnx (отдельный процесс) → поиск корней из выбранного списка → счётчик (counter.json)
        → FastAPI + WebSocket → оверлей OBS (/overlay/) и страница управления (/control/)
```

- **Сервер:** FastAPI + uvicorn на `127.0.0.1:8765` (если порт занят, то 8766-8774).
  Состояние рассылается клиентам по WebSocket `/ws`, команды идут через `/api/*`.
- **Окно приложения:** та же страница `/control/` в окне WebView2 (pywebview),
  плюс значок в трее (pystray). Сервер работает в фоновом потоке (`app/desktop.py`).
- **Распознавание:** в отдельном процессе (`app/stt/worker.py`), чтобы загрузку
  модели можно было прервать мгновенно, просто завершив процесс. Движки (`app/stt/engines.py`):
  Vosk для моделей Vosk и [sherpa-onnx](https://github.com/k2-fsa/sherpa-onnx) для остальных
  (Vosk Streaming, T-one, GigaAM). Потоковые модели выдают текст по ходу речи, GigaAM
  распознаёт фразы целиком, их выделяет детектор речи Silero VAD.
- **Данные пользователя** (`counter.json`, `settings.json`, `wordlists/`, `models/`, `sounds/`,
  `webview/`, `swearcounter.log`) лежат рядом с exe, а при запуске из исходников в корне
  репозитория (`app/paths.py`). Встроенные ресурсы (`overlay/`, `control/`, `assets/`)
  лежат внутри сборки.

## Подготовка окружения

Нужны Windows 10/11, [Python 3.14](https://www.python.org/downloads/) и git.

1. Клонировать репозиторий:

   ```powershell
   git clone https://github.com/vvallikk/SwearCounter.git
   cd SwearCounter
   ```

2. Создать виртуальное окружение `.venv` (на него рассчитаны все команды ниже):

   ```powershell
   py -3.14 -m venv .venv
   ```

3. Поставить зависимости для запуска, тестов и сборки exe:

   ```powershell
   .venv\Scripts\python.exe -m pip install -r requirements-dev.txt -r requirements-build.txt
   ```

   | Файл                     | Что внутри                                    |
   |--------------------------|-----------------------------------------------|
   | `requirements.txt`       | зависимости приложения                        |
   | `requirements-dev.txt`   | + pytest и httpx2 (для `TestClient`)          |
   | `requirements-build.txt` | + PyInstaller                                 |

   Python нужен именно 3.14: под 3.15 у sherpa-onnx пока нет готовых сборок.

4. Модель распознавания скачивается из окна приложения кликом по ней (в папку `models/`,
   она в `.gitignore`). Вручную: распаковать архив так, чтобы получилось
   `models/vosk-model-small-ru-0.22/am, conf, graph, ...`. Ссылки есть в `app/stt/catalog.py`.

## Запуск из исходников

```powershell
.venv\Scripts\python.exe -m app.main
```

Откроется окно и значок в трее, лог пишется в `swearcounter.log`. Выйти можно пунктом
"Выход" в меню трея.

| Ключ             | Что делает                                                 |
|------------------|------------------------------------------------------------|
| `--console`      | без окна и трея: адреса и лог в консоли, выход по `Ctrl+C` |
| `--list-devices` | показать звуковые устройства и выйти                       |
| `--device N`     | слушать устройство с номером `N` или по части названия     |

Для разработки фронтенда удобнее `--console` и обычный браузер:

```powershell
.venv\Scripts\python.exe -m app.main --console
```

- Страница управления: http://localhost:8765/control/
- Оверлей: http://localhost:8765/overlay/

Статика (`overlay/`, `control/`) отдаётся с диска, после правки достаточно обновить страницу.
Python-код требует перезапуска. Второй экземпляр в оконном режиме не запустится
(именованный mutex), сначала закройте первый через "Выход".

## Тесты и CI

```powershell
.venv\Scripts\python.exe -m pytest -q
```

- Тесты лежат в `tests/`, идут пару секунд и не требуют микрофона, моделей и интернета:
  `sounddevice`, `vosk`, `sherpa_onnx` и `urlopen` подменены, файлы создаются во временной папке.
  Работающее приложение и его порты тесты не трогают.
- Новый код ядра (`app/`) покрывается тестами в том же PR.
- GitHub Actions (`.github/workflows/tests.yml`, windows-latest) гоняет тесты на каждый
  PR и push в `main`. Если менялась только документация (файлы `.md`, кроме заметок
  в `docs/releases/`, скриншоты, `LICENSE`, шаблоны issues), тесты пропускаются, а
  обязательная проверка `pytest` засчитывается как пройденная. Файлы `.txt` всегда
  запускают тесты: это зависимости, списки слов и лицензии библиотек.

## Сборка exe локально

1. Закройте запущенный `dist\SwearCounter\SwearCounter.exe` ("Выход" в трее), иначе
   PyInstaller не сможет перезаписать файлы.
2. Соберите:

   ```powershell
   .venv\Scripts\python.exe scripts/build.py
   ```

3. Результат:
   - `dist\SwearCounter\`: готовая папка (`SwearCounter.exe`, `_internal\`, `wordlists\`,
     `README.md`, `LICENSE.txt`, `THIRD_PARTY_LICENSES.txt`, `models\README.txt`);
   - `dist\SwearCounter-v<версия>-windows.zip`: тот же архив, что публикуется в релизе.

Настройки сборки заданы в `SwearCounter.spec` (без консоли, иконка, ресурс версии из
`app/__init__.py`). Иконка перерисовывается скриптом:

```powershell
.venv\Scripts\python.exe scripts/make_icon.py
```

## Выпуск релиза

Релиз собирает и публикует GitHub Actions (`.github/workflows/release.yml`) по тегу `v*`.

1. Обновите `main`:

   ```powershell
   git checkout main
   git pull
   ```

2. Создайте ветку и поднимите версию в `app/__init__.py`. Версия состоит из трёх чисел
   `МАЖОР.МИНОР.ПАТЧ` (семантическое версионирование). Какое число поднять, зависит от релиза:

   | Релиз    | Что в нём                                              | Пример от `1.2.3` |
   |----------|--------------------------------------------------------|-------------------|
   | мажорный | крупные изменения, после которых что-то работает иначе | `2.0.0`           |
   | минорный | новые возможности, прежние работают как раньше         | `1.3.0`           |
   | патч     | только исправления ошибок                              | `1.2.4`           |

   Поднятое число сбрасывает младшие в 0: после `1.2.3` минорный релиз будет `1.3.0`,
   а не `1.3.3`. Ниже для примера выпускается `0.3.0`:

   ```powershell
   git checkout -b release/v0.3.0
   ```

   ```python
   __version__ = "0.3.0"
   ```

   и напишите заметки к релизу в `docs/releases/v0.3.0.md` (без них сборка упадёт).
   Формат как в [v1.0.0](releases/v1.0.0.md): раздел "Что нового" на русском, затем
   "What's new" с тем же списком на английском. Только перечень изменений, понятный
   пользователю, без имён разработчиков и номеров PR. Этот текст увидят пользователи
   на странице релиза и в блоке "Что нового" в программе.

   Там же задаётся [тип обновления](#типы-обновлений): обычное, обязательное для всех
   или обязательное для отдельных версий.

3. Проверьте тесты и закоммитьте:

   ```powershell
   .venv\Scripts\python.exe -m pytest -q
   git add app/__init__.py docs/releases/v0.3.0.md
   git commit -m "Release v0.3.0"
   git push -u origin release/v0.3.0
   ```

4. Откройте PR и влейте его в `main` после зелёных тестов. Ветки `release/*` защищены
   и не удаляются, поэтому мержите без `--delete-branch`:

   ```powershell
   gh pr create --fill
   gh pr merge --merge
   ```

5. Поставьте тег на коммит в `main` и отправьте его:

   ```powershell
   git checkout main
   git pull
   git tag v0.3.0
   git push origin v0.3.0
   ```

6. Следите за сборкой (примерно 5-10 минут):

   ```powershell
   gh run watch
   ```

   Workflow проверит, что тег равен `v` + `__version__` и что есть заметки
   `docs/releases/v0.3.0.md` (иначе упадёт), прогонит тесты, соберёт exe и создаст релиз
   `v0.3.0` с архивом `SwearCounter-v0.3.0-windows.zip` и текстом из заметок.

7. Поправить описание уже опубликованного релиза (в том числе пометку типа обновления):

   ```powershell
   gh release edit v0.3.0 --notes-file docs/releases/v0.3.0.md
   ```

### Типы обновлений

Тег всегда `vX.Y.Z` (его проверяет workflow), а тип обновления задаёт пометка в заметках
`docs/releases/vX.Y.Z.md`. Это HTML-комментарий, на странице релиза и в программе его не видно:

| Пометка | Тип | Что видит пользователь |
|---|---|---|
| нет | обычное | плашка "Доступна vX.Y.Z", обновление можно пропустить |
| `<!-- update: full-force -->` | обязательное для всех | у всех версий ниже этой программа заблокирована до обновления |
| `<!-- update: force 0.2.0 0.2.1 -->` | обязательное для перечисленных | заблокированы только 0.2.0 и 0.2.1, у остальных обновление обычное |

Пометку пишите отдельной строкой в конце файла, одну на релиз. Тест
`test_release_notes_markers_are_valid` проверяет все заметки в `docs/releases/`, так что
опечатка в пометке уронит тесты ещё до выпуска (в программе неверная пометка считается
обычным обновлением).

- Программа смотрит пометки **всех** релизов новее себя: если после обязательной 0.3.0
  вышла обычная 0.4.0, то версия 0.2.0 обязана обновиться (сразу до 0.4.0), а 0.3.0 нет.
- Чтобы сделать обязательным уже вышедший релиз, добавьте пометку в его заметки и выполните
  `gh release edit` из шага 7. Чтобы снять, сделайте то же самое, убрав пометку.
- Блокировка затемняет всю страницу, кроме раздела "Обновления". Сервер не меняет счёт
  и отвечает `423` на изменяющие запросы `/api/*`, кроме `/api/update*`. Работает только
  в собранном exe: из исходников (`frozen=False`) видно лишь предупреждение.
- Галочка "Проверять обновления при запуске" не отключает обязательные обновления:
  без неё программа проверяет релизы тихо и показывает только обязательные.
- Блокировку держит уже установленная программа. Старые версии без этого механизма
  (до v1.0.0) её не умеют, поэтому их релизы удалены с GitHub.

**Если сборка упала:** исправьте причину в `main`, затем удалите тег и поставьте заново:

```powershell
git push --delete origin v0.3.0
git tag -d v0.3.0
git tag v0.3.0
git push origin v0.3.0
```

Если релиз уже успел создаться, сначала выполните `gh release delete v0.3.0 --yes`.

## Как работает обновление

Код находится в `app/updater.py`, API в `/api/update*` в `app/server.py`, интерфейс в разделе
"Обновления" на странице управления и в пункте "Проверить обновления" в трее.

1. **Проверка.** `GET https://api.github.com/repos/vvallikk/SwearCounter/releases?per_page=100`
   без токена (лимит GitHub: 60 запросов в час с IP). Черновики, пре-релизы, теги не вида
   `vX.Y.Z` и релизы без ассета `SwearCounter-v*-windows.zip` игнорируются. Предлагается
   самый новый релиз; обязательность считается по пометкам всех релизов новее текущей версии
   (см. [Типы обновлений](#типы-обновлений)). При запуске проверка идёт не чаще раза
   в 6 часов; время и результат (с версией, для которой он посчитан) хранятся в `settings.json`
   (`update_checked_at`, `update_last`). `update_auto` выключает только показ обычных обновлений.
2. **Скачивание** (только собранный exe): архив качается в `update\update.zip.part`
   и распаковывается в `update\new\`. Прогресс рассылается по WebSocket (`type: "update"`).
3. **Установка.** Пишется `update\apply.cmd` и запускается отдельным процессом, а приложение
   выходит. Скрипт ждёт завершения процесса, копирует `_internal\` (robocopy `/MIR`)
   и `SwearCounter.exe`, запускает новую версию и удаляет папку `update\`.
   Данные пользователя не трогаются.

Версии, вышедшие до появления автообновления, нужно один раз обновить вручную (скачать zip и заменить `SwearCounter.exe` и `_internal`). Версии до v1.0.0 обновляются сами, но обязательных обновлений не понимают.

### Проверить обновление вручную

1. Временно поставьте `__version__ = "0.0.1"` в `app/__init__.py` и соберите exe
   (`scripts/build.py`). Не коммитьте это изменение.
2. Скопируйте `dist\SwearCounter` в отдельную папку, положите туда тестовые
   `settings.json` / `counter.json`, запустите exe.
3. В разделе "Обновления" должна появиться последняя версия. Нажмите "Скачать и установить",
   затем "Перезапустить и обновить". Программа должна перезапуститься с новой версией
   в заголовке, а счёт и настройки должны сохраниться.
4. Верните версию: `git checkout app/__init__.py`.

## Частые задачи

**Добавить модель распознавания.** Допишите её в `CATALOG` в `app/stt/catalog.py`:
название, описание, характеристики, ссылка на архив (`.zip` или `.tar.bz2` с папкой `id`
внутри) и/или отдельные файлы (`files`). Для моделей sherpa-onnx укажите движок (`engine`)
и пути к файлам модели (`model_files`). Модель другого вида sherpa-onnx потребует
нового движка в `app/stt/engines.py`.

**Добавить оформление оверлея.** Добавьте новый пресет в `overlay/presets.js`,
он сам появится в списке на странице управления.

**Сделать личное оформление на заказ.** Это zip-набор, который не попадает в репозиторий
и ставится пользователем из окна программы. Формат, API анимации и лицензия набора описаны
в [PRESETS.md](PRESETS.md). Для проверки положите папку набора в `presets/<id>/` в корне
репозитория (она в `.gitignore`). Готовую папку упакуйте командой
`.venv\Scripts\python.exe scripts/pack_preset.py <папка>`: архив проверяется так же,
как при установке.

**Кнопка "Поддержать".** Ссылки задаются списком `SUPPORT_LINKS` в `app/__init__.py`:
название, адрес и QR-код (картинка в `control/support/`). Если список пустой, кнопки нет
ни в окне, ни в трее. Окно показывает только адреса `https://`. Те же ссылки указаны
в `.github/FUNDING.yml` (кнопка Sponsor на GitHub) и в разделе "Поддержать автора" в README.

**Поменять или добавить встроенный список слов.** Списки лежат в папке `wordlists/` в виде `.txt`
(`swears.txt` это "Маты (18+)", он включён по умолчанию; `parasites.txt` это "Слова-паразиты").
Первая строка `# Название: ...` задаёт название, которое показывает окно программы. Папка
попадает в сборку, при запуске недостающие списки копируются в `wordlists/` рядом с exe
(`app/wordlists.py`). Файлы, которые там уже есть, не перезаписываются ни запуском, ни
обновлением, поэтому правки встроенного списка дойдут только до новых пользователей. Слово
засчитывается, если начинается с корня, поэтому корень не должен быть началом обычного слова.
Проверки лежат в `tests/test_words_file.py`: добавляя корень, допишите туда пару его форм
и похожих обычных слов. `words.txt` старых версий при первом запуске переносится в `my.txt`
(или удаляется, если это была тестовая заглушка).

**Добавить зависимость.** Впишите её в `requirements.txt`. Её лицензия попадёт в
`THIRD_PARTY_LICENSES.txt` сама (`scripts/licenses.py` берёт тексты из пакетов). Если
пакет приносит библиотеки не из pip или не кладёт в себя текст лицензии, опишите их в
`EXTRAS` там же, а текст положите в `scripts/third_party/`. Код программы распространяется
под GPL-3.0, поэтому зависимости должны быть с совместимой лицензией (MIT, BSD, Apache-2.0,
LGPL и т. п.).

**Переснять скриншоты для README** (`docs/screenshots/`). Запустите приложение с `--console`
и снимите страницу и оверлей headless-браузером. Каждому снимку нужен свой `--user-data-dir`,
а файл появляется через несколько секунд после выхода команды. Например:

```powershell
& "${env:ProgramFiles(x86)}\Microsoft\Edge\Application\msedge.exe" --headless=new --user-data-dir="$env:TEMP\edge-shot" --hide-scrollbars --virtual-time-budget=5000 --window-size=560,2400 --screenshot="$PWD\docs\screenshots\control.png" http://localhost:8765/control/
```

Окно снимается по вкладкам: `control.png` (`/control/#counter`), `control-look.png`
(`/control/#look`) и `control-settings.png` (`/control/#settings`). Высота взята с запасом,
пустой фон снизу потом обрежьте.

## Структура проекта

```
app/main.py           точка входа, ключи запуска, логирование
app/desktop.py        окно (pywebview), трей (pystray), сервер в потоке, один экземпляр
app/server.py         FastAPI: /ws, /api/state, /api/increment, /api/reset, /api/speech,
                      /api/devices, /api/sound, /api/overlay, /api/words, /api/update,
                      /api/presets/custom, статика
app/custom_presets.py личные оформления: установка zip-наборов в presets/, упаковка и экспорт
app/preset_links.py   установка оформления по ссылке: Яндекс Диск, Google Диск, Dropbox
app/updater.py        проверка, скачивание и установка обновлений из GitHub Releases
app/settings.py       настройки (settings.json)
app/sound.py          громкость и библиотека звуков оповещения (sounds/)
app/counter.py        счётчик и сохранение в counter.json
app/wordlists.py      списки слов (wordlists/): раскладка встроенных, выбор активного
app/profanity.py      поиск корней из списка (перечитывается при изменении),
                      счёт по ходу фразы (SwearTracker)
```
